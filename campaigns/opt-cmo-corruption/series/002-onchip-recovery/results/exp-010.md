**Scoped verdict:** LR tuning over this grid does not rescue the dense
idealized-write recipe at 256 updates on the tested array. The original full
pass at 5e-3 also worsened performance, while digital LoRA improved it. These
observations do not establish that all physical adaptation fails. A matched
diagnostic that disables incremental write noise would help separate optimizer
behavior from write-error accumulation before expanding the sweep; this is a
proposed intervention, not a completed or authorized additional experiment.
As in exp-008, the many out-of-range states limit physical interpretation of
the unclamped fitted noise law. The retrospective audit below identifies a
large update-to-noise mismatch; its causal contribution remains untested.

## Retrospective write-law audit

The October 12 read-only audit examined the implemented law and the saved
optimizer of the best development screen, LR 3e-3 at update 256. It launched no
new training and changed no scientific configuration or selection decision.
The native checkpoint SHA-256 was verified as
`8b79d4e21dd6de1b49c584d2dbb0bd87cb260f92e6934d50fb657ff214b1f586`.
CPU reconstruction from its saved Adam first and second moments gives the
following scales in normalized weight units:

| Quantity | Value |
| --- | ---: |
| Final intended Adam command, RMS across healthy active devices | 0.00071607 |
| Final intended Adam command, mean absolute magnitude | 0.00056240 |
| Per-write noise standard deviation at mid-range | 0.01413954 |
| RMS of fitted noise standard deviations evaluated at the held endpoint | 0.01537733 |

The mid-range noise scale is approximately **20 times the final command RMS**.
This is a last-step comparison, not a trajectory-wide estimate or a measurement
of the realized random draw. The endpoint-based noise scale is not the exact
pre-write scale. Healthy cells are identified by nonzero cumulative writes,
which include initial programming; exactly zero commands receive no new noise.
The JSON audit includes per-matrix values and sampled command quantiles at
`results/lifecycles/opt125m-cmo-l6-exp4-dense-lr/readiness/write-update-audit.json`.

`CmoMatrix.write` applies `G <- G + delta_G + sigma(G + delta_G) * normal`
to every healthy active cell with a nonzero command. The noise scale depends
on conductance, not command magnitude. The held conductance carries previous
errors; there is no clean digital target, verify loop or conductance clamp.
Lowering LR shrinks intended corrections without proportionally shrinking
write noise. Nearly all healthy active cells are written at every step:
approximately 7.03 billion writes in this 256-step screen. This mechanism is
consistent with the nonmonotonic LR results, but does not by itself prove
causation or rule out optimization/gradient issues.

The source fit describes programming error around a target after a
program-and-verify procedure; it does not establish an incremental pulse law
([AIHWKit 1.1.0 source](https://github.com/IBM/aihwkit/blob/v1.1.0/src/aihwkit/inference/noise/reram.py)).
Applying that fit as fresh additive error at every incremental write is the
explicit idealization in the [CMO contract](../../../../../docs/reram_cmo_device.md),
not a newly discovered violation of the declared implementation. Its physical
validity needs separate evidence, especially as states leave the fitted range.
Successful replay validates reproducibility, not that physical extrapolation.

HWA updates a digital master and resamples temporary forward perturbations;
its programming error does not accumulate in that master. LoRA leaves the
physical array held and learns a digital correction, including compensation
around stuck cells. Their success therefore does not establish that this dense
physical-write law should improve, or that their LR values transfer directly.

The next discriminating diagnostic would preserve the exact noisy, faulty P0
and vary **incremental** write noise only, with fixed-cohort development checks
early in adaptation. A forced noise-only write control could isolate write
exposure; setting LR to zero is insufficient because the current implementation
then skips all writes. These are proposed interventions, not completed results
or additional authorized GPU work. A favorable noiseless diagnostic would
justify examining the write law and update sparsity, not claiming physical
on-chip viability.

## Operational failure and correction

Incident 12, `storage_observation_failed`, began around 02:00 Paris. The
automatic storage probe looked for a GPU placement on every storage target.
This campaign has remote GPU placements and a prepared local collection root;
the missing local GPU placement raised `StopIteration`, recorded as an empty
error string. The initial manual storage observation admitted two screens, then
became stale. Admission correctly stopped on stale storage, but the observation
bug prevented the remaining screens from running before their 07:30 deadline.

The persistent watchdog remained alive and successfully invoked its bounded
read-only investigator. Investigation `869ef36e7f1e44a092a1355014db25a0`
reported the storage failure and recommended repairing observation before
further dispatch. It had no authority to change code or extend time. Its report
and original incident remain in the durable ledger. The interactive handoff
receipt checked active workers but missed this campaign-level incident and
did not require a successful automatic storage observation. Its `passed` claim
was insufficient; the earlier completion estimate was wrong.

The correction uses the prepared local collector checkout for local storage
probes, preserves remote placements, and includes target, paths, working
directory and exception type in future error evidence. Four new regression
cases reproduced the missing-collector failure before the fix and test success,
missing preparation, a nonlocal fallback rejection and storage I/O failure.
Root dispatcher plus LR-decision checks pass 149 tests; the deployed older
service checkout passes 132 dispatcher tests. Root fix: `0dc61cc`; service fix:
`7c0af1e`. The frozen training source, manifests, completed results, selection
criteria and deadlines are unchanged. Recovery evidence is retained in
`readiness/storage-recovery-{before-restart,after-restart,resolution}.json`.
The restarted service automatically observed all storage roots successfully

That repair did not automatically restart expired experiments. The subsequent
user instruction explicitly reopened the three missing screens and the existing
